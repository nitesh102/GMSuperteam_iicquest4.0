1.  SYSTEM ARCHITECTURE
================================================================================

1.1  High-Level Architecture
─────────────────────────────

  Browser ──Inertia.js──▶ Laravel 11 (REST/JSON) ──Eloquent──▶ MySQL
     │                        │
     │                        ├── Controllers (CRUD)
     │                        ├── Middleware (Auth, Session, HandleInertia)
     │                        ├── Spatie Permissions (RBAC)
     │                        └── Validation (inline)
     │
     └── Vue 3 SPA (Composition API)
         ├── Pages/       (per-route page components)
         ├── Components/  (shared — Modal, Sidebar, DataTable)
         ├── Layouts/     (AuthenticatedLayout, GuestLayout)
         └── Inertia App  (app.js + Ziggy routes)

  Data flow:
    Page visit          → GET /{route} → Controller::index() → Inertia::render()
    Form submit (create) → POST /{route} → Controller::store() → redirect + flash
    Form submit (update) → PUT /{route}/{id} → Controller::update() → redirect + flash
    Delete              → DELETE /{route}/{id} → Controller::destroy() → redirect + flash

  Optimistic CRUD flow:
    User action → local state update (instant) → HTTP request (background)
    → redirect sync → props update → watch re-syncs local state

1.3  Key Architectural Decisions
─────────────────────────────────

  • Inertia.js SPA: No API endpoints; server returns JSON page data or redirects.
  • Modal-based CRUD: No create/edit/show routes; all CRUD via modals on index page.
  • Client-side list management: Search, sort, paginate entirely on frontend via
    computed properties on a local reactive `items` ref.
  • Optimistic updates: Local list mutated instantly; server syncs via redirect.
  • Props sync: A `watch` on `usePage().props` catches server-side changes after
    redirect and re-syncs the local `items` ref (critical fix for temp-ID bug).
  • Flash messages: Shared via HandleInertiaRequests middleware, displayed as a
    fixed-position toast, auto-dismiss after 4s, reactive via watch.

2.  OPTIMIZATION ANALYSIS
================================================================================

2.1  Database / Eloquent
─────────────────────────
  ✓ Eager Loading         : ComplaintCategory::with('department') in controller.
  ✓ Pagination            : Client-side for small datasets (~8 items).
                            For >100 items, switch to server-side ->paginate().
  ✓ Indexes               : Primary keys indexed. Foreign keys (department_id,
                            created_by, updated_by) could benefit from explicit indexes.
  ✓ Soft Deletes          : ComplaintCategory uses SoftDeletes trait.
  ✓ Query Scopes          : Not used. Consider local scopes if filter patterns emerge.

2.2  Caching
─────────────────────────
  ✗ No caching strategy implemented.
    - Department and ComplaintCategory lists are fetched on every page load.
    - Cache::remember('departments.all', 3600, ...) recommended for read-heavy pages.
    - Cache::forget(...) on store/update/destroy to invalidate.
  ✗ Route/config caching not configured for production.

2.3  Frontend Performance
─────────────────────────
  ✓ Vite code splitting : Each page is a separate chunk (lazy-loaded).
  ✓ Tree-shaking        : ES module imports, only used code bundled.
  ✓ Client-side sort/search/paginate : Zero server round-trips for data filtering.
  ✓ Optimistic CRUD     : Local state updates instantly, no wait for server.
  ✓ Props sync watch    : Prevents temp-ID items from persisting after redirect.

2.4  Bundle Sizes (production build)
─────────────────────────────────────
  app.js                ~281 kB (gzip: ~100 kB) — Vue, Inertia, Ziggy, FontAwesome
  Pages/Department/Index.vue  ~15.7 kB (gzip: ~4.7 kB)
  Pages/ComplaintCategory/Index.vue  ~16.8 kB (gzip: ~4.9 kB)
  Components/DepartmentModal.vue     ~4.7 kB (gzip: ~1.8 kB)
  Pages/ComplaintCategory/ComplaintCategoryModal.vue  ~6.1 kB (gzip: ~2.1 kB)

2.5  Recommendations
─────────────────────
  1. Add server-side pagination when dataset exceeds 100 records.
  2. Implement cache layer: Cache::remember for department/category lists.
  3. Add database indexes on foreign keys and created_at.
  4. Use queue for email/notification dispatch in future features.

3.  SECURITY ANALYSIS
================================================================================

3.1  Authentication & Authorization
────────────────────────────────────
  ✓ Laravel Breeze (secure auth scaffolding, bcrypt hashing, CSRF protection).
  ✓ Inertia auto-handles CSRF tokens on every request.
  ✓ Spatie Permission installed and seeded (RolePermissionSeeder).
  ✓ All CRUD routes behind 'auth' middleware group.

  ✗ No authorization gates on DepartmentController or ComplaintCategoryController.
    - Any authenticated user can create/update/delete any entity.
    - Recommendation: Add Spatie middleware or Laravel Policies:
        $this->middleware('permission:manage departments');
        $this->middleware('permission:manage complaint categories');

3.2  Input Validation
─────────────────────
  ✓ Both controllers validate: required, string, max:255/max:1000.
  ✓ Mass-assignment protected via $fillable.
  ✓ Existence checks: 'department_id' => 'exists:departments,id'.
  ✓ XSS prevented: Inertia + Vue auto-escape all data.

  ✗ No dedicated Form Request classes — validation inline (acceptable for current
    complexity, extract when rules grow).

3.3  SQL Injection
─────────────────────
  ✓ Eloquent ORM with parameterised queries. No raw DB::raw() found.

3.4  CSRF / XSS / File Upload
─────────────────────────────
  ✓ CSRF: Handled by Laravel + Inertia.
  ✓ XSS: Auto-escaped by Inertia/Vue. No v-html usage.
  N/A File uploads: Not implemented yet.

3.5  Additional Concerns
─────────────────────────
  • created_by / updated_by are set from $request->user()->id — safe.
  • Soft deletes on ComplaintCategory prevent data loss.
  • No rate limiting on CRUD endpoints (consider throttle middleware).
  • No audit/activity logging (consider spatie/laravel-activitylog).

5.2  Known Bugs & Resolutions
───────────────────────────────

  BUG-001: DELETE /departments/{id} → 404
    Root cause: Departments table had no data (fresh migration). Route model
    binding could not resolve the ID, returning 404.
    Fix: Created DepartmentSeeder with 8 realistic departments, called from
    DatabaseSeeder. Used `firstOrCreate` for idempotent re-seeding.
    Status: RESOLVED.

  BUG-002: Temp negative-ID items appear in list after optimistic create
    Root cause: Optimistic create adds an item with `id: -Date.now()` to the
    local `items` ref. When Inertia reuses the component (same-page navigation
    after redirect), the <script setup> does NOT re-execute, so `items` retains
    the temp item. The new server props are available via usePage().props but
    never synced to the local ref. If the user clicks edit on the temp item, a
    PUT request to `/entities/-1781092532978` returns 404.
    Fix: Added `watch(() => usePage().props.{entity}, v => items.value = [...(v ?? [])])`
    to sync local state whenever server props change after redirect.
    Status: RESOLVED in both Department and ComplaintCategory Index.vue.

  BUG-003: Flash messages not showing on edit/delete
    Root cause: When Inertia reuses the component after a redirect, the
    <script setup> doesn't re-run, so `flashMessage` ref stays null. Only
    the initial page load captured the flash value.
    Fix: Changed from direct ref initialization to `watch(() => usePage().props.flash?.success, ...)`
    with `{ immediate: true }`. The watch fires both on mount (initial value) and
    on every prop update (after redirect). Also fixed auto-dismiss timer to be
    reset on each new flash.
    Status: RESOLVED.
